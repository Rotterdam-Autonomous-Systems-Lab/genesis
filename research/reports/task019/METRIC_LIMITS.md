# Interpretation of the frozen Task 019 instrumentation

These observations qualify the comparison; they do not change frozen inputs, model source or resource caps mid-run. Finite ledger/client conformance remains separately checkable. A complete native resource/proof claim is not established by a PASS label alone.

- `operations.signatures` counts actual worker Ed25519 verification calls; client signature checks are separate. `decodes` counts shared parser calls, including repeated wrapper construction/validation. These are prototype work counts, not independent native VM instruction counts.
- `hashed_bytes` counts signed-input/terms-verification paths. Stateless identity/output-ID hashing is not fully instrumented. It is **incomplete**, cannot compare total hashing work and must not be interpreted as zero uncounted work. Timed worker CPU includes those helpers.
- Account `writes` counts changed top-level tables; object `writes` counts resource replacements; UTXO `writes` counts consumed plus created outputs. These units differ and must not be ranked as equivalent writes. `reads` counts explicit adapter lookup calls, not all interpreter memory accesses or serialization work.
- `native_state_bytes` is the high-water serialized native store/history file. The immutable public term/key/alias registry and label caches reside in the context; their memory contributes to process RSS but their serialization is excluded from that file. Report a separately derived registry size. This is not a demonstrated fully durable native state store or production data-availability design.
- UTXO retains spent-output data and registry successors; accounts/objects retain more compact history records. Archival feature parity is not established. Their native file sizes are representation descriptors, not a fair family-wide storage ranking.
- Worker/client component CPU excludes projection/debug serialization, as declared. Per-process CPU limits do not prove an aggregate CPU-group120s limit. Harness peak RSS is not recorded by the frozen instrumentation. Those missing measurements/controls require qualification/HOLD; no caps may be silently increased.
- macOS reports measured RSS but cannot enforce the same hard memory/CPU-affinity controls as Linux here. Its resource profile is not an equivalent reference-profile pass. Cross-platform deterministic outcomes can still reproduce.
- Server-assisted reference/wrapper construction is counted in worker work and proxy traffic. The client does not construct/verify full native state/finality proofs. No production constrained-client capability follows. Inputs are pre-signed; live signing/key-isolation costs are not measured.
- Recovery reloads a fsynced client journal after discarding volatile state. It does not kill/power-cycle a validator database or establish crash-safe native-store persistence. The scheduler's positive finality/fencing observations are explicit axioms, not implemented consensus or non-execution proofs.
- A resource timeout is inconclusive. The trace preserves checked barriers and the error; a transition at the failing boundary may have happened before observation/trace completion. Do not infer definitive non-inclusion from a timeout or count its unchecked last state as verified. Retain the prefix, source/input identities and failure for reproduction.

The narrow operation language is implemented in host Python, not a general object VM or external-transaction UTXO script engine. The corpus is finite; arbitrary malformed programs, generalized key rotation/recovery, parallel execution, pruning, real networking, physical services, economic demand and consensus remain outside acceptance.

## Recipient-pool counterexample

`probe_recipient_pool.py` reuses `pay12` then `pay8`: the second transaction, signed by D2, consumes S's existing12-unit balance output and replaces it with20 for S, without S's signature. The logical payment conserves value and preserves S's owner/value, but the implementation is a **coalesced recipient-pool profile**, not a conventional owner-signature coin-spend model. A public top-up covenant could permit this behavior; that covenant is not separately specified or validated against arbitrary untrusted successor proposals here. Merely storing `lock=S` is not evidence of that script's enforcement.

Preserve this [counterexample](recipient-pool-counterexample.json). No frozen expectation or measured model is changed to conceal it. Do not credit normal UTXO input independence or general script/ownership security from this adapter. This is an unresolved implementation/security-model limitation and a G1 qualification/HOLD, not a defect in the extended-UTXO family or evidence for eliminating it. Task020 must independently specify/validate the covenant or replace recipient coalescing with append-only recipient outputs, then re-establish the comparison under reviewed source identities and budgets.
